# Inter-Company Stock Transfer (`intercompany_stock_transfer`)

Odoo 18.0 (Community or Enterprise) addon that lets **explicitly authorized
users** move stock from a location of one company to a chosen location of
another company in the same database. Every movement goes through native
`stock.picking` / `stock.move` / `stock.move.line` records, with company
boundaries and valuation intact.

* Depends only on `stock`. If `stock_account` is installed, valuation is
  handled natively (see *Accounting*).
* Does not modify core files or any other module's behaviour. Only pickings
  generated by a transfer get extra checks.

---

## 1. Architecture

| Component | Purpose |
|---|---|
| `intercompany.stock.transfer` | Header: reference (`ICT/YYYY/NNNNN`), source company (+ optional branch)/warehouse/location, destination company (+ optional branch)/warehouse/location, date, responsible, remarks, status, audit fields, chatter. |
| `intercompany.stock.transfer.line` | Product, UoM, requested qty, optional lot/serial, plus computed *reserved / dispatched / in transit / received* and *source availability*. No separate balance is stored: every figure is computed from the stock moves. |
| `stock.picking` (extended) | `intercompany_transfer_id` link and a stored `intercompany_role` (dispatch, receipt, return to source, return from destination). Guards on `_action_done`, `action_cancel` and `unlink`. |
| `stock.move` (extended) | `intercompany_line_id` link. It is copied on backorders, returns and push moves, so the link survives native splits. |
| `intercompany.stock.transfer.cancel` | Wizard that records the cancellation reason. |

### Companies and branches

Each side has a **Company** dropdown (top-level companies the user is allowed
in) and a **Branch** dropdown, shown only when that company has branches the
user can access. The company that actually owns the stock is stored in
`source_company_id` / `dest_company_id`: the branch if one is chosen,
otherwise the company. In Odoo a branch is a company, so stock, valuation and
security rules apply to it exactly as to any other company.

* With only a Company chosen, the warehouse list shows that company's
  warehouses **and its branches' warehouses**. Picking a branch warehouse fills
  in the Branch automatically.
* Choosing a Branch (or clearing it, meaning "main company") limits the
  warehouses to exactly that company. Locations are always restricted to the
  chosen warehouse.
* Supported: company ↔ company, branch ↔ other company, branch ↔ branch,
  company ↔ its own branch.
* The dropdowns list every company the user is allowed in, **whatever is
  ticked in the company switcher**. The fields send `allowed_company_ids` set
  to the user's companies, and Odoo itself refuses any company the user is not
  allowed in.

### How the stock moves

Odoo forbids a single stock move between two companies (`stock_account`
raises *"they are doing an intercompany in a single step"*). The module uses
the native shared **`Inter-company transit`** location
(`stock.stock_location_inter_company`, `usage=transit`, no company). Odoo
activates it automatically as soon as a second company exists. No new
locations or operation types are created.

```
Company A                         shared                       Company B
[selected source location] --(A delivery)--> [Inter-company transit] --(B receipt)--> [selected dest. location]
```

1. **Confirm** creates the **source operation** in company A: the source
   warehouse's *Delivery* type, from the selected location to Inter-company
   transit. It is confirmed and reserved with the native engine. No stock moves
   yet, and the two operations are **not** validated automatically.
2. **Dispatch** validates the source operation with the native
   `button_validate`, so the normal lot/serial and backorder wizards apply.
   Stock leaves A and sits in transit.
3. When a dispatch is validated, from the transfer form or from Inventory, the
   **destination receipt** is generated in company B: the destination
   warehouse's *Receipt* type, from transit to the selected location. It
   contains exactly the quantities and lots that were dispatched, and its
   moves are chained (`move_orig_ids`) to the dispatch moves for traceability.
4. **Receive** validates the receipt. Stock enters B only at this point.

The receipt is created at dispatch time, not at confirmation, on purpose. The
transit location bypasses reservation, so a receipt prepared up front would be
fully "ready" before anything shipped and could add stock to the destination
that never left the source. This matches what Odoo Enterprise's own
`sale_purchase_stock_inter_company_rules` does.

**Multi-step reception:** if the destination warehouse uses 2- or 3-step
reception, the receipt goes to `WH/Input` with `location_final_id` set to the
selected location. The native push rules then carry the goods through the
warehouse steps to that location. No warehouse operation is bypassed.

### Integrity guards (all entry points: transfer form, Inventory UI, RPC)

Checked inside `stock.picking._action_done` for pickings linked to a transfer.
An error rolls back the whole validation.

* The transfer must be confirmed, and must not be cancelled (for dispatches).
* Dispatched lines must come from the selected source location or one of its
  sub-locations and go to Inter-company transit.
* **Availability:** on hand at the exact location/lot/package/owner, minus
  what *other* operations have reserved, must cover the quantity. Odoo would
  otherwise allow negative stock or take another operation's reservation.
* Net dispatched quantity never exceeds the requested quantity. This blocks
  duplicated pickings and quantities increased by hand.
* Received or returned quantity never exceeds what is in transit, **per
  lot/serial**.
* Receipt lines must land in the destination location (one-step) or in the
  destination warehouse (multi-step).
* The transfer row is locked (`SELECT … FOR UPDATE`) during workflow actions,
  so concurrent clicks serialize. Every action is idempotent: confirming twice
  creates one operation, dispatching twice raises *nothing left to dispatch*,
  and receipt generation skips dispatch moves that already have a receipt.

### Statuses

| Status | Meaning |
|---|---|
| Draft | Editable; nothing generated. |
| Confirmed | Source operation created and reserved; nothing dispatched. |
| In Transit | Something has been dispatched and not everything is received yet (or a source backorder is still open). |
| Received | All dispatched stock is validated in the destination and nothing is left to dispatch. |
| Cancelled | Cancelled with a reason (see below). |

Partial flows use native backorders on both sides. If a backorder is
declined, the remaining quantity stays visible *In Transit*, and **Receive
Stock** creates a new receipt for it.

### Cancellation

* Before dispatch: the open source operation is cancelled. It is kept, not
  deleted, for traceability.
* After a (partial) dispatch: open operations are cancelled and the quantity
  still in transit is **not** reversed silently. A **return operation** is
  created in the source company (transit → source location, carrying the
  in-transit lots, linked through `origin_returned_move_id` so it is valued at
  the original cost). It must be validated when the goods are physically back.
* Received transfers cannot be cancelled. Use the native *Return* on the
  destination receipt; the transfer then shows the quantity back in transit.
* Linked pickings cannot be deleted. Transfers can be deleted only in Draft, or
  when Cancelled with no operations. Otherwise archive them.

## 2. Access control

* Group **Allow Inter-Company Stock Transfers**
  (`intercompany_stock_transfer.group_intercompany_transfer`) is a native
  `res.groups` record in its own category under *Inventory*. In **Settings →
  Users & Companies → Users → Access Rights** (no debug mode needed), the
  *Inventory* section shows **Inter-Company Stock Transfers: [ blank |
  Allow Inter-Company Stock Transfers ]**. Blank means not allowed.
* The group implies *Inventory / User*. Inventory users do **not** get it
  automatically.
* `ir.model.access.csv`: only this group can access the transfer, line and
  wizard models. Everyone else is refused by the ORM, including over
  XML-RPC/JSON-RPC.
* The menu *Inventory → Operations → Inter-Company Transfers* and its window
  action are restricted to the group.
* Global record rules: a transfer and its lines are visible only if the source
  **or** the destination company (or branch) is one of the companies the user
  is allowed in (`user.company_ids`). This doesn't depend on the company
  switcher, and nothing of other companies is visible.
* Server-side checks in every workflow method and on the linked pickings,
  whatever screen or API is used:
  * create / edit / confirm / check availability / dispatch / cancel:
    group **and** access to **both** companies;
  * receive: group and access to the destination company (lets a store keeper
    of company B receive);
  * validating or cancelling a linked picking from the standard Inventory
    screens needs the same rights. Ordinary inventory users can still *see*
    those pickings, as usual.
* Companies are activated with `allowed_company_ids`, and Odoo itself rejects
  companies the user is not allowed in. `sudo()` is used only for read-only
  aggregates (quantities in transit, counters, availability shown in the form)
  and for consistency validation. No write is done in sudo.

## 3. Accounting and valuation (when `stock_account` is installed)

* Source → transit is valued as an **outgoing** move of company A (like a
  delivery). Transit → destination is an **incoming** move of company B (like
  a receipt). Each company gets its own valuation layer and, with automated
  valuation, its own journal entry in its own journal and accounts:
  * A: Dr *Stock Output* (category, or the transit location's valuation
    account if configured) / Cr *Stock Valuation*.
  * B: Dr *Stock Valuation* / Cr *Stock Input*.
* The receipt is priced at the **actual cost removed from A** (its valuation
  layers), converted from A's currency to B's at the dispatch date. AVCO/FIFO
  products in B take that cost. Standard-price products in B use B's standard
  price, which is native behaviour.
* Returns to source are valued at the original dispatch cost.
* Nothing is valued in B before the receipt is validated. One valuation layer
  per move; no duplicates (covered by tests).

**Limitation, by design.** This is a *physical* transfer. The module creates
no sale order, purchase order, invoice or vendor bill. With automated
valuation, the interim balances (A: Stock Output, B: Stock Input) stay open
until inter-company invoicing settles them. If legal ownership changes and the
companies must invoice each other, either:

* use Odoo Enterprise's `sale_purchase_inter_company_rules` /
  `sale_purchase_stock_inter_company_rules` (SO ↔ PO with synchronized
  delivery and receipt) for those flows, or
* book the inter-company invoice manually against those interim accounts.

For a clean ledger, an accountant can set dedicated inter-company accounts as
the *valuation accounts* of the Inter-company transit location.

## 4. Installation / upgrade

The module lives in `/home/odoo/odoo18/addons/intercompany_stock_transfer`
(mounted as `/mnt/extra-addons` in the `odoo18-odoo-1` container).

```bash
# install on a database (example: <db>)
docker exec odoo18-odoo-1 bash -c 'odoo -c /etc/odoo/odoo.conf --db_password="$PASSWORD" \
    -d <db> -i intercompany_stock_transfer --stop-after-init --no-http'
# upgrade after code changes
docker exec odoo18-odoo-1 bash -c 'odoo -c /etc/odoo/odoo.conf --db_password="$PASSWORD" \
    -d <db> -u intercompany_stock_transfer --stop-after-init --no-http'
docker restart odoo18-odoo-1
```

Or: *Apps → Update Apps List → search "Inter-Company Stock Transfer" →
Activate*. Back up the database first.

**Prerequisites**

* At least two companies, so the *Inter-company transit* location is active.
* Each warehouse used has its Delivery (source) and Receipt (destination)
  operation types (default for every warehouse).
* Products must be **storable** and either shared (no company) or owned by a
  common parent company of both companies. Lots/serials of shared products are
  shared, so the same lot record continues into the destination.
* Grant users the right (see §2) and give them access to both companies
  (and the branches they use). They don't need to tick them in the company
  switcher.

## 5. Usage

1. *Inventory → Operations → Inter-Company Transfers → New*.
2. Choose the source Company (and Branch if needed) → Warehouse → Location,
   then the same for the destination. Changing a company, branch or warehouse
   clears incompatible selections.
3. Add products and quantities (optional lot/serial). *Source Availability*
   shows the free quantity at the location and its sub-locations.
4. **Confirm Transfer**, then **Check Availability** if needed. To dispatch
   partially or choose serials, open the *Source Picking* smart button and
   adjust it.
5. **Dispatch Stock** (backorder wizard if partial). The *Destination Picking*
   smart button appears.
6. **Receive Stock** (or validate the receipt in company B).
7. Follow everything in the chatter and the *Traceability* tab.

## 6. Tests

```bash
docker exec odoo18-odoo-1 bash -c 'odoo -c /etc/odoo/odoo.conf --db_password="$PASSWORD" \
    -d <throwaway_test_db> -i stock_account,intercompany_stock_transfer \
    --test-tags /intercompany_stock_transfer --stop-after-init --http-port=8099'
```

Never run tests on a production database. `tests/` covers: creation by
authorized users; refusal for unauthorized users (ORM/RPC, linked pickings,
menu); granting/revoking the right from the user form; warehouse/location
domains and onchanges; server-side rejection of invalid
company/warehouse/location/product/UoM/quantity combinations; multiple lines;
UoM conversion; insufficient stock and other operations' reservations; source
decrease on dispatch and destination increase only on receipt; picking
companies; lots and serials; partial flows with accepted and declined
backorders; multi-step reception; cancellation before and after dispatch with
return; idempotent and repeated actions; duplicated pickings; native returns
from the destination; company boundaries; valuation layers, real-time journal
entries per company, return valuation and currency conversion.
